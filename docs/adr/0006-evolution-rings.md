# Skill evolution happens in rings, and the top gate is permanently human

John's skills should improve from run evidence, but a bad edit to a meta-skill silently degrades every future project — so evolution is structured by blast radius. **Ring 0** (this project): Claude maintains a lessons ledger, drafts project-local skill overrides (applied at phase-boundary sign-off; autonomously only in endurance mode with a strong, always-reported reason), and may *train* workerLLM skills with a scored, strictly-gated, bounded-edit loop where the domain ships a scorer. **Ring 1** (a template): the template's owner evolves it semi-automatically from accumulated run reports — the template is the unit of domain learning, and app feedback (end-user-judged runtime results + expert-judged build-process quality) is its signal. **Ring 2** (John core + the authoring methodology): evolves only by human analysis over collected evidence; never by an automated loop. Influence travels upward as evidence (lessons, reports — scrubbed of corpus content at every ring boundary), never downward as automatic edits. The trainable surface is defined by philosophy, not whitelist: text a different domain's template author could legitimately have written differently is trainable; text true in every domain is teaching, and only Ring 2 touches it. The evaluation surface — the process scorecard's rubric, the reducer's gates, the event contract — lives outside every automated edit surface: no skill edit can change what counts it. The human top gate is not scaffolding to be automated away later; it is the design — every documented catastrophe in self-evolving text systems involves unbounded self-editing against a gameable evaluator, and every working system bounds its edits, validates on held-out evidence, and keeps a gate the optimizer cannot touch.
