# kc-rule-schema — KC's rule shape as a domain-specific example

KC (the verification harness, sibling project to John) ships rule-shaped knowledge. The schema is worth knowing as one well-tested example of a domain-specific knowledge format.

## The rule shape

A rule in KC has roughly:

- `id` — sequential, used in references (e.g., R001)
- `source_ref` — exact citation to a regulation or policy
- `description` — one-line summary of what the rule says
- `applicable_sections` — scope classifiers (which docs / contexts this rule applies to)
- `severity` — high / medium / low
- `machine_checkable` — is the rule testable by an algorithm? (boolean)
- `falsifiability_statement` — what's the precise condition under which the rule fails?
- `test_case_stub` — a sketch of how to test the rule on a sample document
- `source_chunk_ids` — evidence chunks from the source material that anchor this rule
- `related_rules` — cross-references to other rules (dependencies, prerequisites)

Plus a `glossary` (per project) for shared vocabulary.

## Why this works for verification

- **`source_ref` + `source_chunk_ids`** anchor the rule to evidence. Required for compliance work.
- **`falsifiability_statement`** makes the rule mechanically checkable. Without this, you can't run an algorithm against it.
- **`test_case_stub`** seeds the testing phase. Bridges from extraction to evaluation.
- **`related_rules`** + glossary handle the rule-graph dimension (one rule depends on another's terminology).

## Why this doesn't generalize

If you're not building verification apps, most of these fields are wrong:

- A factual statement doesn't have a `falsifiability_statement` in any useful sense.
- A storyline doesn't have `source_chunk_ids` because the source IS the storyline.
- A skill (procedural) doesn't have `severity`.

Take the *idea* (atomic units, source-anchored, testable, cross-linked, glossary-supported) but invent the fields to fit your format.

## Generalizable patterns from KC's rule design

These transfer to any schema:

1. **Source anchoring is mandatory.** Every entry should be traceable back to where it came from. The field names vary; the practice doesn't.
2. **Testability where possible.** If an entry can be checked mechanically, include the check in the schema (test_case_stub, expected_output, etc.). Worth the field even when the runtime doesn't test automatically.
3. **Cross-references between entries.** Knowledge is rarely orthogonal. Add fields for "this entry relates to X."
4. **Shared vocabulary lives in a glossary.** Cheaper than repeating definitions per entry.
